# 特性迁移技术方案

本文档基于上游 AnvilCraft 源码与网易 ModSDK 官方文档，梳理各玩法系统在基岩版中的实现方式、技术改造点与 API 限制。

上游源码与官方接口索引见 [sources.md](sources.md)，分阶段推进与验收标准见 [development-plan.md](development-plan.md)。原版铁砧的两条方块粉碎配方已通过网易 3.10 PC 客户端实测。[复测记录](development.md#复测原版铁砧粉碎)

## 特性迁移矩阵

表格中的“迁移方式”分为四类：
- **直接配置**：使用基岩版自定义方块、物品、特征或静态配方 JSON 即可实现。
- **脚本重写**：保留玩法规则，使用 ModSDK 服务端事件、方块实体数据与自定义 UI 重新实现。
- **原型验证**：依赖未实测的底层接口或存在较大性能风险，需在阶段 0 或阶段 5 先做独立实验。
- **内部替代**：上游用于对接其他 Java 模组的接口，在基岩版中改为模组内置 UI 或自用接口。

## 核心系统实现设计

### 铁砧下落与配方结算

上游通过 `FallingBlockEntityMixin` 在铁砧落地时抛出 `AnvilEvent.OnLand`，由 `AnvilEventListener` 依次分发切石机破坏、多步加工、世界配方与特定方块响应（S5）。在网易基岩版中，我们在服务端建立统一的下落跟踪与配方结算模块，将引擎底层下落事件封装为包含维度、落点坐标、下落高度、下方加工台方块和周围掉落物列表的结算上下文。

网易自定义重力方块需要配置 `base_block: custom_heavy_block` 与 `netease:fall.send_python_event: true`，引擎会触发开始下落、落地还原、变更为掉落物和落地伤害四个事件（N2、N3）。落地事件虽然带有 `fallTickAmount`，但精确下落高度仍需记录开始下落时的起始坐标并与落点坐标求差。主包也通过 `AddEntityServerEvent` 识别原版铁砧的下落实体，跟踪脚下方块，在实体消失后核对落点是否实际出现铁砧，再按同一实体 ID 结算。覆盖完整、开裂和损坏的原版铁砧，专用重力事件与实体事件共用同一条下落记录。[网易世界事件](https://mc.163.com/dev/mcmanual/mc-dev/mcdocs/1-ModAPI/事件/世界.html) · [实体类型接口](https://mc.163.com/dev/mcmanual/mc-dev/mcdocs/1-ModAPI/接口/实体/实体类型.html#getentitynbttags)

配方表在服务端启动时按加工类型、下方平台方块和输入物品 ID 建立内存索引。单次铁砧下落最多触发一次结算：先校验所有输入物品和方块仍然存在、数量充足且输出位置可容纳，校验通过后一次性扣除输入并生成产物。若物品带有附魔、耐久或自定义 `userData`，先完整读取其数据字典，再按具体配方规则保留或修改字段。

阶段 1 首批验证以下四个典型配方：

| 上游配方文件 | 输入与产出 | 服务端验证要点 |
| --- | --- | --- |
| `recipe/block_crush/gravel.json` | 圆石 → 沙砾 | 准确识别落点下方块，单次下落只替换一次 |
| `recipe/block_crush/sand.json` | 沙砾 → 沙子 | 产物本身为重力方块时，与下一次下落事件的触发顺序不冲突 |
| `recipe/item_compress/bone_block.json` | 3 个骨头 → 1 个骨块 | 合并多个掉落物实体的堆叠数量，正确扣除并保留多余骨头 |
| `StampingRecipe` | 冲压平台 + 对应原料 → 冲压产物 | 校验下方平台方块类型，平台不匹配时拒绝结算 |

### 磁铁、容器与方块实体存档

上游 `MagnetBlock` 在未充能时搜索下方一定距离内的铁砧并将其吸至磁铁正下方，充能后释放下落（S6）。基岩版实现时需同时处理已放置的铁砧方块和正在下落的铁砧实体，通过服务端状态锁避免两个相邻磁铁同时捕获同一个铁砧，并保证悬停状态下断电、拆毁磁铁、区块卸载重载后铁砧不会丢失或复制。

容器与物流系统先对接原版箱子、木桶和漏斗，再扩展到自定义容器。调用 `GetContainerItem` 时，`getUserData` 参数默认为 `False`（N7）；搬运可能带有附魔或自定义数据的物品时必须显式传入 `getUserData=True`，并在写回目标容器后核对数据完整性。

机器运行状态通过 `CreateBlockEntityData` 的扩展数据接口持久化（N4、N5），统一记录数据格式版本号、加工进度和缓存资源量。修改嵌套字典或列表后必须对顶层键重新赋值才能触发引擎保存；超出 32/64 位整数上限的数值转为十进制字符串存储。当区块卸载或玩家退出存档时，`GetBlockEntityData` 会返回 `None`，服务端逻辑需立即中止当前刻的处理并在区块重新加载时恢复状态。

### 电网、流体管网与结构操作

电网和流体管网在服务端维护按维度和区块划分的无向连接图（S7、S8）。仅在放置或破坏节点方块、开关阀门或区块加载状态变化时重建受影响的连通分量；常规 Tick 只按缓存的连通分量汇总发电量、耗电量与流体传输量。未加载区块中的节点不参与计算，待区块加载后再重新并网。

结构扫描器与移动结构依赖 `GetBlockPaletteBetweenPos` 和 `SetBlockByBlockPalette` 接口（N10）。根据网易文档，床、门等双格方块在调色板操作中有特殊行为，且冲突模式下生成可能中途终止。执行批量方块操作前必须先检查目标区域加载状态与可替换性，记录操作日志以便失败时恢复。

## 网易 ModSDK 接口限制与应对策略

| 接口或特性 | 官方文档说明的行为 | 项目应对策略 |
| --- | --- | --- |
| 重力方块事件（N2、N3） | 必须开启 `send_python_event`；伤害在落地瞬间计算，下落途中无实体间逐帧碰撞回调 | 阶段 0 实测原版铁砧与自定义铁砧的事件触发情况；巨型铁砧与弹射物碰撞单独编写检测逻辑 |
| `ServerBlockEntityTickEvent`（N3、N4） | 固定每秒触发 20 次，仅在玩家模拟距离或常加载区内触发；退出存档时数据接口可能返回空 | 耗时计算采用降频分摊；所有 Tick 逻辑先判空，妥善处理区块边界卸载 |
| 自定义方块实体数据（N5） | 不支持 `tuple`；`dict` 键必须为 `str`；`list` 内元素类型必须一致；修改嵌套结构需重新赋值给顶层键；大整数需转字符串 | 封装统一的读写辅助函数，自动校验类型、转换大整数并在写回时重赋顶层键 |
| 原版方块实体 NBT（N5） | `CreateBlockInfo` 的 `GetBlockEntityData` 返回原版底层 NBT 结构，字段随基岩版引擎升级可能变动 | 模组机器一律使用 `CreateBlockEntityData`；仅在读写原版特殊方块时集中调用 `CreateBlockInfo` |
| `GetBlockNew` / `SetBlockNew`（N6） | 仅能操作已加载区块；直接用 `SetBlockNew` 替换容器方块会清空内部物品（即使方块 ID 与附加值相同） | 改变机器外观状态时使用方块状态（BlockState）或实体数据，禁止直接调用 `SetBlockNew` 覆盖带库存的方块 |
| 容器读写接口（N7） | `GetContainerItem` 与 `SpawnItemToContainer` 对支持的容器类型有限制，末影箱需使用专属接口 | 在阶段 0 逐一测试原版容器、自定义容器与原版漏斗的交互兼容性 |
| 红石信号接口（N3、N8） | 自定义机械元件可接收 `BlockStrengthChangedServerEvent`，通过 `GetStrength` 读取 0–15 信号强度 | 阶段 0 验证磁铁、探测器等方块作为红石源和红石负载时的信号传递表现 |
| `AddRecipe` 动态配方（N9） | 官方文档注明动态注册配方在联机大厅模式下无效 | 所有基础合成配方一律生成静态 JSON 文件放入 `behavior_pack/recipes/`；铁砧加工由服务端脚本自行匹配 |
| 方块调色板（N10） | 对床、门及方块冲突有特殊处理，批量生成可能执行一半后失败 | 限制单次扫描与放置的最大体积，操作前预检容器与多方块结构 |
| `CreateDimension` 自定义维度（N11） | 支持创建自定义维度，维度 ID 需按规则注册 | 将月球等天体维度放入阶段 5 独立制作原型，验证地形生成与客户端天空渲染 |

移植静态配方时需建立 Java 版与基岩版的标识符映射表，逐一核对原版物品命名差异（如染色、木材变种、工具组件）、展开 `#c:*` 与 `#minecraft:*` 标签，并映射炼药锅状态。基岩版缺失的原版特性或联动输入需替换为本模组自定义物品，或推迟到后续阶段实现。上游 `anvillib_recipe:in_world_recipe` 与代码动态生成的配方在迁移时统一转换为结构化的 Python 配置表。

代码遵循 `LICENSE`（LGPL-3.0-or-later），美术与音频等非代码资产遵循 `ASSETS_LICENSE`（默认保留所有权利，详见 [NOTICE.md](../NOTICE.md)）。开发阶段若直接复制上游纹理、模型、音效或语言文件，必须在资源清单中登记源文件路径、作者与授权状态。

项目主线优先交付阶段 1 至阶段 4 的稳定玩法；阶段 5 的高风险特性在完成独立原型验证后，再逐项决定全量合入、缩减范围合入或暂缓发布。
